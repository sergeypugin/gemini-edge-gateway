## Архитектура Two-Zone Split без разбора всего JSON

При активной работе агента в контекст попадают десятки прочитанных файлов и изображений в формате base64. Объем входящего тела запроса может достигать 20--35 Мегабайт.

На бесплатном тарифе Cloudflare Workers действует жесткий лимит: не более 10 миллисекунд процессорного времени (CPU time) на один запрос.

### Бенчмарки на реальном теле 24 МБ (8 фотографий)

В ходе тестирования были проведены замеры производительности трех подходов на одинаковом дампе:
- классический `JSON.parse` + обход дерева + `JSON.stringify` занял **79.97 мс** (гарантированное падение воркера с ошибкой `Error 1102: Worker exceeded resource limits`)
- глобальные регулярные выражения по всей строке заняли **20.27 мс** (падение по лимиту CPU из-за накладных расходов сборщика мусора на копирование 24 МБ строк)
- метод **Two-Zone Split** выполнил обработку за **1.5--4.2 мс** (успешное выполнение с неплохим запасом)

Это исторические замеры, а не новый бенчмарк текущей реализации со структурным сканированием сигнатур.

### Как устроен Two-Zone Split
Тело запроса состоит из двух принципиально разных частей:
- зона метаданных (первые 15--30 Килобайт), содержащая системный промпт, настройки reasoning, сообщения ассистента и вызовы тулов
- зона тяжелых бинарников (остальные 24+ Мегабайт), представляющая из себя массив ответов инструментов с base64 внутри

Алгоритм находит границу первого изображения через нативный строковый поиск:
```javascript
const imgIdx = rawText.indexOf('"image_url"');
let cutoff = rawText.length;

if (imgIdx !== -1) {
  const msgStart = rawText.lastIndexOf('{"role"', imgIdx);
  cutoff = msgStart !== -1 ? msgStart : imgIdx;
}

let metaZone = rawText.slice(0, cutoff);
let dataZone = rawText.slice(cutoff);
```

Регулярные выражения не ограничены `metaZone`: в ней нормализуется `reasoning_effort`, а в `dataZone` регулярное выражение заменяет `role: "tool"` на `role: "user"`. Дополнительно `reasoning_effort` нормализуется в последних 1000 символах `dataZone`. После склейки `addMissingToolSignatures` структурно сканирует весь текст, но вызывает `JSON.parse` только для найденных массивов `tool_calls`, а не для всего тела с base64. При подмене модели регулярное выражение применяется только к первым 500 символам шаблона. Размер `metaZone` определяется расположением первого изображения и не имеет жесткого ограничения в 30 КБ.

Подготовка очищенного шаблона выполняется ровно один раз перед началом перебора моделей. В самом цикле каскада меняется только строка с именем модели в начале документа, что занимает менее 0.1 мс.

### Fast-Path приоритизация моделей и ключа

Fastpath изменяет порядок кандидатов, а не сохраняет точную успешную пару:
- последняя успешная модель хранится отдельно для каскадов smart и lite в `lastSuccessfulSmartModel` и `lastSuccessfulLiteModel`
- `lastSuccessfulKeyId` общий для обоих каскадов, поэтому успех в lite может изменить приоритет ключа для следующего smart-запроса и наоборот
- модель перемещается в начало только своего каскада, если она еще входит в него и не находится в `deadModels` или активном `modelCooldowns`; ключ перемещается в начало, если еще входит в `activeKeys`
- при переборе по-прежнему проверяются блокировки модели, ключа и пары; приоритет не гарантирует успех первой попытки

Все три переменные находятся в памяти конкретного isolate Worker. Они не записываются в D1, не являются глобальными между isolate и не сохраняются надежно при пересоздании isolate или deploy.

При успешном HTTP-ответе с телом роутер обновляет fastpath, пишет `Success`, статистику и статус `200` после принятия первого чанка тела, до завершения стрима. Первый чанк не обязательно содержит полезный токен или завершенное SSE-событие. Последующий обрыв стрима не отменяет уже записанный успех.

## Особенности Google Protobuf адаптера и thought_signature

> [!note]
> При проектировании шлюза были учтены следующие проблемы совместимости, зафиксированные сообществом на официальном форуме Google AI Developers:
> - [Gemini 3.1 Pro Preview: public image URLs return 403 / native 400 OpenAI compatible while inline images work](https://discuss.ai.google.dev/t/gemini-3-1-pro-preview-public-image-urls-return-403-native-400-openai-compatible-while-inline-images-work/183023) -- разбор причин сбоя валидации при передаче ссылок на изображения и необходимости инлайнинга base64
> - [Gemini 3.6 Flash: OpenAI-compatible token limits, response fields and auth keys](https://discuss.ai.google.dev/t/gemini-3-6-flash-openai-compatible-token-limits-response-fields-and-auth-keys/183372/2) -- анализ форматов ответов адаптера OpenAI, сигнатур мыслей и расхождения полей квот

При обращении к Gemini через эндпоинт `/v1beta/openai/chat/completions` Google использует внутренний транслятор из JSON в Protobuf. В нем есть две недокументированные особенности, вызывающие ошибку `HTTP 400 INVALID_ARGUMENT`:

### 1. Поле content: null
В спецификации OpenAI ассистент при вызове инструментов отправляет сообщение с `"content": null`. Промежуточный транслятор Google ожидает строковое значение или массив частей. Значение `null` вызывает сбой валидации схемы. Шлюз заменяет `null` на пустую строку `""`.

### 2. Сигнатуры мыслей (Thought Signatures)
В моделях поколения Gemini 3 при включенном рассуждении (thinking) Google внедряет криптографическую подпись рассуждений в поле `extra_content.google.thought_signature`. Редактор Zed, работающий по стандартной спецификации OpenAI, вырезает это поле при сохранении истории.

При отправке следующего сообщения Google проверяет историю тулов и при отсутствии сигнатуры выдает ошибку:
`Function call is missing a thought_signature in functionCall parts`.

Шлюз вызывает структурный обработчик из `src/lib/tool-signatures.js` после склейки зон:
```javascript
return addMissingToolSignatures(metaZone + dataZone);
```

Обработчик сканирует JSON-строки с учетом экранированных кавычек и обратных слешей, поэтому текст `tool_calls` или скобки внутри строковых аргументов не воспринимаются как структура. Для свойства `"tool_calls"` с массивом он находит закрывающую скобку с учетом вложенных массивов и строк, затем разбирает только этот массив через `JSON.parse`.

Для каждого вызова с `type: "function"` существующее непустое `extra_content.google.thought_signature` сохраняется. Если сигнатура отсутствует или пуста, добавляется `"skip_thought_signature_validator"`, с сохранением остальных полей `extra_content` и `google`. Измененные массивы сериализуются обратно; остальной текст тела и корневой блок `tools` не переписываются этим обработчиком.

Маркер skip -- совместимый fallback для обхода проверки, а не настоящая подпись и не восстановление утраченного состояния рассуждений. Старый regex-подход, который искал конец массива без учета JSON-строк и пропускал весь массив при наличии любой сигнатуры, больше не используется.

## Таймауты стрима и метрики TTFB и RESPONSE

`fetchWithStreamTimeout` в `src/lib/upstream.js` возвращает тело upstream как поток и отслеживает время его получения и завершения. В логах Worker и дашборде показываются две отдельные метрики:

| Поле | Семантика |
| :-- | :-- |
| `ttfb_ms` / `ttfbMs` | время от начала попытки `fetch` до первого непустого чанка тела Google, включая ожидание заголовков и отправку запроса |
| `response_ms` / `responseMs` | время от первого непустого чанка тела до EOF исходного тела Google |

Это время между Worker и Google, а не до первого полезного токена, не полная задержка, видимая в Zed, и не сумма только сетевого времени без пауз. Первый чанк может содержать только часть SSE-события. `response_ms` включает ожидания между чанками и остаётся неизвестным, пока чтение тела не завершится.

Значения сохраняются в одной записи `logs`: сначала записываются `ttfb_ms` и `response_ms = NULL`; после нормального EOF продолжительность записывается в ту же строку по её D1 `id`. Если стрим прерван, клиент отменил запрос, тело не содержит байтов или время неизвестно, соответствующее поле остаётся SQL `NULL`. Публичный API передаёт `null`, а сайт отображает его как `-`; прочерки в БД не хранятся. Для старых строк миграция добавляет оба новых поля с `NULL` и удаляет старую колонку `duration_ms`.

Таймауты применяются в два этапа:
- до первого непустого чанка действует единый абсолютный лимит 60 секунд от запуска fetch, включая ожидание заголовков; получение заголовков не перезапускает таймер
- после первого чанка каждое последующее ожидающее чтение тела получает отдельный лимит 60 секунд; между чтениями таймер выключен, поэтому длительный активный стрим разрешён и общего лимита в 60 секунд на генерацию нет
- отмена запроса клиентом передаётся upstream и не замораживает модель
- `TimeoutError` до первого байта замораживает модель на 5 минут и переключает каскад на следующую модель; `ttfb_ms` в таком случае остаётся `NULL`
- обрыв или idle timeout после передачи успешного ответа логируется отдельно и не блокирует модель; запись успеха сохраняет известный `ttfb_ms`, а `response_ms` остаётся `NULL`

Успех, статистика и статус `200` фиксируются после получения первого непустого чанка, а не после завершения генерации. Успешный, но оборванный после начала поток поэтому может иметь `ttfb_ms`, `response_ms = NULL` и статус `200`; отдельный warning фиксирует прерывание.

Исторические `duration_ms` не переименовываются в `ttfb_ms`, поскольку они измерялись до заголовков и не содержат времени первого байта. Миграция удаляет их без заполнения новых полей; старые значения после перехода не сохраняются.

## Мультимодальные ответы инструментов в Zed

Когда агент Zed выполняет инструмент `read_file` для изображения, он присылает результат в сообщении следующего вида:
```json
{
  "role": "tool",
  "content": [
    {
      "type": "image_url",
      "image_url": { "url": "data:image/jpeg;base64,..." }
    }
  ]
}
```

Google Protobuf-адаптер строго запрещает передачу объектов `image_url` внутри роли `tool` и возвращает ошибку `400: Invalid content part type: image_url`. Ответ инструмента обязан быть текстом.

Шлюз трансформирует роль таких блоков:
- сообщения ответов тулов, содержащие изображения, переименовываются в `role: "user"`
- текстовые описания и подтверждения сохраняются
- мультимодальный блок становится обычным пользовательским изображением, которое зрение Gemini 3 нативно считывает без ошибок валидации схемы

## Миф о Pacific Time и сброс суточных квот в 00:00 UTC

В документации Google указано, что суточный лимит запросов (20 RPD) сбрасывается в полночь по Тихоокеанскому времени (Pacific Time).

Однако анализ реальных ответов Google при ошибке 429 опровергает это утверждение. В теле ошибки поле `RetryInfo` указывает точное количество секунд до разблокировки:
```json
{
  "@type": "type.googleapis.com/google.rpc.RetryInfo",
  "retryDelay": "14558s"
}
```

Сопоставление текущего времени со значением `retryDelay` показывает, что серверы Google целятся строго в **00:00:00 по Всемирному координированному времени (UTC)**, что соответствует **03:00:00 по Московскому времени (UTC+3)** независимо от времени года.

Если бы шлюз ориентировался на полночь по Тихоокеанскому времени (10:00--11:00 МСК), ключи оставались бы в искусственном бане на лишние 7--8 часов после того, как Google уже фактически обнулил счетчик, поэтому шлюз использует прямое вычисление полуночи по UTC:
```javascript
function getNextMidnightUtc() {
  const d = new Date();
  d.setUTCHours(24, 0, 0, 0);
  return d.getTime();
}
```

### Защита от рассинхронизации серверов Google

Суточные лимиты бесплатных ключей Google AI Studio обнуляются строго в `00:00 UTC`. Однако из-за распределенной архитектуры серверов Google квоты на некоторых нодах могут обновляться с задержкой в несколько минут.

Если ключ совершает запрос в `00:15 UTC` и получает ошибку `RPD`, шлюз применяет специальную защитную логику:
- Если ошибка `RPD` получена в интервале **00:00 -- 00:01 UTC**, ключ блокируется не до конца суток, а ровно до **`01:01 UTC`** (таймаут на 1 час или менее для компенсации рассинхрона).
- Это дает серверам Google гарантированное время на обновление квот на всех балансировщиках и возвращает ключи в строй максимально быстро, не заставляя ждать новые сутки.

Однако из-за непредвиденных сбоев API, временных рассинхронизаций или ложных срабатываний реализована дополнительная проверка времени предыдущей разблокировки. Если последний бан для пары модель-ключ был снят час назад или менее, то ключ отправляется в кулдаун не до полуночи, а всего на один час:
```javascript
if (lastUnblock > 0 && Math.abs(nowMs - lastUnblock) < ONE_HOUR_MS) {
  unlockTime = nowMs + ONE_HOUR_MS;
}
```

## Лимиты subrequests в Cloudflare и порционная валидация

В бесплатном тарифе Cloudflare Workers действует жесткое правило: один входящий запрос к воркеру может инициировать не более **50 исходящих вызовов `fetch()` (subrequests)**. На 51-м запросе рантайм аварийно завершает работу воркера.

### Как распределен бюджет подзапросов
- в боевых запросах генерации (`/v1/chat/completions`) сетевая валидация ключей отключена полностью (расход равен 0 подзапросов)
- лимит попыток каскадного перебора ограничен константой `MAX_SUBREQUESTS = 40`, что гарантирует запас до аварийного порога платформы
- при проверке ключей в веб-дашборде (`/api/stats`) валидация выполняется пачками не более чем по 40 ключей за один заход
- если в конфигурации указано 50 или 100 ключей, первые 40 опрашиваются сразу, а остальные помечаются как `UNCHECKED (?)`
- фронтенд дашборда автоматически шлет повторный запрос на `/api/stats?validate_next=true` для следующей пачки, открывая новый чистый бюджет в 50 подзапросов
- все полученные статусы сохраняются в таблицу D1 `keys_cache` на 24 часа, благодаря чему при обычных перезагрузках страницы расходуется ровно 0 сетевых вызовов

## Кольцевой буфер D1 на базе нативного триггера SQLite

Хранение логов в реляционной базе требует очистки старых записей, чтобы не превысить бесплатную квоту хранения (500 МБ) и лимит чтения строк (5 000 000 rows read в день).

Попытка выполнять удаление через подзапрос вида:
```sql
DELETE FROM logs WHERE id NOT IN (SELECT id FROM logs ORDER BY id DESC LIMIT 5000);
```
приводит к тому, что при каждой операции вставки движок вынужден сканировать все 5000 строк. При 1000 запросах в день это сжигает 5 000 000 операций чтения, полностью исчерпывая суточный лимит D1 на холостых проверках.

### Инженерное решение через первичный ключ B-Tree
В таблице `logs` первичный ключ `id` является автоинкрементным монотонно возрастающим числом (`INTEGER PRIMARY KEY AUTOINCREMENT`).

Если текущий идентификатор равен `N`, то пятитысячная запись с конца гарантированно имеет номер `N - 5000`. Поиск по первичному ключу `id <= (N - 5000)` в дереве SQLite выполняется за логарифмическое время без единого чтения тела строк.

Очистка автоматизирована на уровне базы данных через триггер, срабатывающий пачками по 100 записей:
```sql
CREATE TRIGGER IF NOT EXISTS prune_old_logs_trigger
AFTER INSERT ON logs
WHEN (NEW.id % 100 = 0 AND NEW.id > 5000)
BEGIN
  DELETE FROM logs WHERE id <= (NEW.id - 5000);
END;
```

Преимущества такого подхода:
- нулевой расход CPU на уровне JavaScript (воркер выполняет только `INSERT`)
- ровно один раз на каждые 100 вставок триггер мгновенно удаляет 100 устаревших строк одним пакетом
- объем таблицы строго стабилизирован в диапазоне от 5000 до 5100 записей вне зависимости от даты их создания

## Фильтрация мыслей (Thinking) в стриме SSE

В `src/lib/stream.js` реализована потоковая фильтрация блоков рассуждений (`<thought>`, `<thinking>`, `<think>`):

```javascript
if (inThought) {
  const closeMatch = str.match(/<\/(thought|thinking|think)>/i);
  if (closeMatch) {
    inThought = false;
    initialThoughtFinished = true;
    return str.slice(closeMatch.index + closeMatch[0].length);
  }
```

Шлюз осознанно вырезает промежуточный процесс мышления и не отправляет его в редактор по нескольким причинам:
- **экономия токенов в контексте чата**: сохраненные мысли захламляют историю последующих сообщений, быстро расходуя ценное окно контекста и приближая лимит TPM (250k токенов в минуту на бесплатном тарифе)
- **чистота интерфейса Zed**: блоки мыслей иногда не сворачиваются в интерфейсе чата и вылезают в рабочее окно редактора, отвлекая и мешая чтению итогового ответа или кода
- **простота и надежность реализации**: клиентский UI в сторонних редакторах требует сложной поддержки кастомных аккордеонов для сворачивания размышлений, тогда как чистый ответ рендерится мгновенно и без артефактов

> [!important]
> Это никак не снижает качество ответов модели. Модель по-прежнему полностью выполняет весь цикл внутренних рассуждений (reasoning / thinking) на стороне Google перед генерацией ответа. Шлюз лишь убирает эти рассуждения из финального стрима SSE.

> [!warning]
> Текущая реализация фильтрации основана на потоковых регулярных выражениях. В сложных сценариях (многоходовые вызовы инструментов, специфические форматы ответов Google или обрывы стрима) блоки мыслей могут просачиваться в итоговый ответ.

## Динамическое автообнаружение новых моделей (Discovery)

В `src/lib/discovery.js` заложена автоматическая поддержка любых новых версий Gemini без необходимости обновлять код шлюза:

```javascript
// src/lib/discovery.js
const isChatModel = (name) => /^gemini-\d+(\.\d+)?-(flash|flash-lite)(-preview)?$/i.test(name.toLowerCase());
```

Как работает механизм обнаружения:
- регулярка  подхватывает как существующие модели (`gemini-3.8-flash`, `gemini-3.5-flash-lite` и т.д.), так и любые будущие релизы Google (`gemini-4.0-flash`, `gemini-4.5-flash-lite` и т.д.)
- найденные модели сортируются по версии в порядке убывания и разбиваются на два пула: `smart` (полноразмерные Flash модели) и `lite` (облегченные Lite модели)
- список моделей кэшируется на сутки, минимизируя сетевые запросы к Google API
- Актуальный состав каскадов и полный список доступных Google моделей всегда можно посмотреть в реальном времени на веб-дашборде по якорной ссылке: `https://gemini-edge-gateway.your-name-in-cloudflare.workers.dev/#smart-cascade`
